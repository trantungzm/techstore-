CHƯƠNG 1. GIỚI THIỆU
1.1. Mục đích
Tài liệu này cung cấp thiết kế chi tiết về kiến trúc, các lớp xử lý, dữ liệu cũng như các mối ràng buộc giữa các thực thể dữ liệu trong hệ thống Website kinh doanh thiết bị công nghệ TechStore.
Tài liệu này được sử dụng để:
Nhân viên kiểm thử: Lập kịch bản test và số liệu test dựa trên thiết kế các chức năng, luồng nghiệp vụ và ràng buộc dữ liệu.
Thành viên đội phát triển: Xây dựng và hiện thực các phân hệ nghiệp vụ chức năng theo đúng thiết kế lớp và thiết kế dữ liệu.
Nhân viên thiết kế GUI: Tham khảo để thiết kế giao diện khu cửa hàng (Store) và khu quản trị (Admin).
Khách hàng: Xác nhận tính đúng đắn của thiết kế so với yêu cầu đã được đặc tả.
1.2. Phạm vi
Tài liệu này phục vụ cho việc phát triển và bảo trì dự án TechStore — hệ thống thương mại điện tử bán thiết bị công nghệ, được xây dựng theo kiến trúc microservice (API Gateway, AuthService, APIService) với giao diện người dùng dạng Single Page Application.
Phạm vi gồm: kiến trúc tổng thể và phân tầng; xác thực (JWT) và phân quyền (RBAC); thiết kế lớp; thiết kế cơ sở dữ liệu; thiết kế giao diện. Tài liệu không bao trùm hạ tầng triển khai sản xuất và tích hợp thanh toán thật của bên thứ ba (hiện dùng luồng QR mô phỏng).

CHƯƠNG 2. TỔNG QUAN HỆ THỐNG
TechStore là website kinh doanh thiết bị công nghệ cho phép khách hàng tìm kiếm, so sánh, đặt mua sản phẩm trực tuyến và sử dụng các dịch vụ hậu mãi (bảo hành, sửa chữa, hỗ trợ). Đặc thù mặt hàng công nghệ là mỗi đơn vị sản phẩm có định danh duy nhất (Serial/IMEI) và chính sách bảo hành theo từng máy, nên hệ thống quản lý tồn kho ở mức từng đơn vị vật lý.
2.1. Tổng quan
Hệ thống theo kiến trúc microservice: SPA (React/Vite) ⇄ API Gateway (Ocelot) ⇄ AuthService &amp; APIService ⇄ SQL Server (EF Core). Các module nghiệp vụ chính: Product, Inventory, Order, Coupon, Warranty, Repair, Support (Ticket), Notification, Auth (quản lý người dùng &amp; phân quyền) và Dashboard.
2.2. Các yêu cầu chức năng
Use-case model
Hệ thống có 5 tác nhân (Khách vãng lai là tác nhân phụ theo SRS):
Tác nhân
Mô tả
Khách vãng lai (phụ)
Chưa đăng nhập; xem/tìm/so sánh sản phẩm, tra cứu bảo hành, gửi ticket
Khách hàng
Đã đăng nhập; đặt hàng, thanh toán, theo dõi đơn, gửi yêu cầu bảo hành
Kỹ thuật viên
Tiếp nhận và xử lý bảo hành, sửa chữa, ticket kỹ thuật
Quản trị viên kho
Nhập hàng, quản lý Serial/IMEI, tồn kho, đổi trả
Quản trị viên hệ thống

CHƯƠNG 3. KIẾN TRÚC HỆ THỐNG
3.1. Mô hình kiến trúc
Hệ thống theo kiến trúc microservice, tách biệt Client và Backend; mọi yêu cầu đi qua API Gateway; các dịch vụ backend chia sẻ chung cơ sở dữ liệu qua tầng Repository/EF Core.

Hình 3.1: Sơ đồ các thành phần của phần mềm TechStore
Client (Frontend)
SPA React/Vite gồm khu Store và Admin; giao tiếp HTTP (axios) và realtime qua SignalR; gắn JWT ở header Authorization.
API Gateway
Ocelot tiếp nhận và định tuyến yêu cầu tới dịch vụ downstream, phục vụ tệp tĩnh SPA. Gateway chỉ định tuyến, không tự xác thực JWT — token được kiểm tra ở downstream.
AuthService
Xác thực và quản lý người dùng; phát hành JWT chứa định danh và vai trò.
APIService
Xử lý nghiệp vụ chính theo phân tầng Controller → Service → Repository; host SignalR Hub và background service xử lý đơn nhận hàng quá hạn.
Repositories / Database
Lớp Repository (EF Core) ánh xạ entity ↔ bảng qua AppDbContext; CSDL SQL Server techstore. Migration áp dụng thủ công.
Lưu ý: Quyết định kiến trúc: mô hình “microservice chia tiến trình nhưng dùng chung CSDL” (shared database) — điểm lệch có chủ đích so với database-per-service nhằm đơn giản hóa trong phạm vi đồ án.
3.2. Cơ chế xác thực (Authentication)
JWT Bearer do AuthService phát hành; mật khẩu băm PBKDF2 (HMAC-SHA1, 10.000 vòng, có salt); token ký HMAC-SHA256, chứa claim định danh/tên đăng nhập/vai trò, hạn 8 giờ; mọi dịch vụ xác thực bằng cùng khóa bí mật.
Lưu ý: Rủi ro bảo mật: mã nguồn còn nhánh so khớp mật khẩu plain-text cho tài khoản cũ chưa có salt — khuyến nghị loại bỏ trước khi triển khai thật.

4.9. Thiết kế chi tiết các hàm (giả mã &amp; sơ đồ khối)
1. QUY ƯỚC TRÌNH BÀY
Theo yêu cầu, mô tả một hàm chỉ bằng tên và một dòng là chưa đủ; cần mô tả chi tiết cách hàm thực hiện. Mỗi hàm dưới đây trình bày theo cấu trúc: chữ ký → bảng đặc tả (Mục đích, Đầu vào, Đầu ra, Tiền/Hậu điều kiện) → giả mã từng bước → sơ đồ khối.
Ký hiệu sơ đồ khối: hình bo tròn = Bắt đầu/Kết thúc; hình chữ nhật = bước xử lý; hình thoi = điều kiện rẽ nhánh (Đúng/Sai); hình bình hành = vào/ra dữ liệu (return); nhánh phụ tô hồng = ném ngoại lệ (throw).
CopyFrom(entity) : void
Mục đích
Sao chép giá trị các thuộc tính từ một thực thể nguồn sang thực thể hiện tại
Đầu vào
entity: thực thể nguồn cùng kiểu
Đầu ra
void
Tiền điều kiện
entity cùng kiểu
Hậu điều kiện
Các thuộc tính (trừ khóa chính) của đối tượng = giá trị của entity
Giả mã (pseudocode):
HÀM CopyFrom(entity) TRẢ VỀ void
BẮT ĐẦU
    NẾU entity == null THÌ KẾT THÚC
    VỚI MỖI thuộc tính p CỦA đối tượng hiện tại LẶP
        NẾU p KHÔNG PHẢI khóa chính (Id) VÀ entity CÓ thuộc tính p THÌ
            this.p ← entity.p
    HẾT LẶP
KẾT THÚC
2. MODULE AUTH – XÁC THỰC &amp; PHÂN QUYỀN
Authenticate(username, password) : User | null
Mục đích
Xác minh đăng nhập, trả về người dùng hợp lệ
Đầu vào
username, password
Đầu ra
User nếu hợp lệ, ngược lại null
Tiền điều kiện
username, password không rỗng
Hậu điều kiện
Trả về User khi mật khẩu khớp (PBKDF2 hoặc plain-text legacy)
Giả mã (pseudocode):
HÀM Authenticate(username, password) TRẢ VỀ User | null
BẮT ĐẦU
    NẾU username rỗng HOẶC password rỗng THÌ TRẢ VỀ null
    user ← userRepository.GetByUsername(username)
    NẾU user == null THÌ TRẢ VỀ null
    NẾU user.Salt CÓ dữ liệu THÌ
        isValid ← IsValidPassword(password, user.Salt, user.Password)   // PBKDF2
    NGƯỢC LẠI
        isValid ← (password == user.Password)        // tài khoản cũ chưa băm
    NẾU NOT isValid THÌ TRẢ VỀ null
    TRẢ VỀ user
KẾT THÚC

BẮT ĐẦU

3. MODULE ORDER – ĐẶT HÀNG
CreateOrder(userId, dto) : OrderDetailDto
Mục đích
Tạo đơn: trừ tồn, tính tiền, áp coupon, lưu đơn
Đầu vào
userId (nullable), dto
Đầu ra
OrderDetailDto
Tiền điều kiện
dto hợp lệ; còn hàng
Hậu điều kiện
Đơn + dòng hàng + timeline lưu trong 1 transaction; tồn đã trừ
Giả mã (pseudocode):
HÀM CreateOrder(userId, dto) TRẢ VỀ OrderDetailDto      // chạy trong TRANSACTION
BẮT ĐẦU
    ValidateCreateOrder(dto);  subtotal ← 0;  details ← []
    VỚI MỖI item TRONG dto.Items LẶP
        product ← productRepo.GetById(item.ProductId)
        NẾU product == null HOẶC NOT product.IsActive THÌ NÉM lỗi &quot;không khả dụng&quot;
        NẾU item CÓ VariantId THÌ
            NẾU variant.Stock &lt; item.Quantity THÌ NÉM lỗi &quot;Hết hàng&quot;
            rows ← variantRepo.DecrementStock(variant.Id, item.Quantity, variant.Version)  // optimistic lock
        NGƯỢC LẠI
            NẾU product.TotalStock &lt; item.Quantity THÌ NÉM lỗi &quot;Hết hàng&quot;
            rows ← productRepo.DecrementStock(product.Id, item.Quantity, product.Version)
        NẾU rows == 0 THÌ NÉM lỗi &quot;Xung đột cập nhật / hết hàng&quot;
        subtotal ← subtotal + (variant?.Price ?? product.BasePrice) * item.Quantity
        THÊM OrderDetail(...) VÀO details
    HẾT LẶP
    shippingFee ← (giao tại cửa hàng) ? 0 : phí ship mặc định
    NẾU có coupon THÌ
        NẾU userId == null THÌ NÉM lỗi &quot;cần đăng nhập&quot;
        kq ← couponService.Validate(userId, ...);  NẾU NOT kq.IsValid THÌ NÉM lỗi kq.Message
        productDiscount ← kq.ProductDiscount;  shippingDiscount ← kq.ShippingDiscount
    total ← subtotal − productDiscount + shippingFee − shippingDiscount
    orderRepo.Add(order);  orderRepo.AddDetails(details);  THÊM OrderTimeline(&quot;Pending&quot;)
    couponService.CommitOrderCoupons(order.Id, kq)
    TRẢ VỀ MapToDto(order)
KẾT THÚC

7.3. Kết luận
Tài liệu thiết kế chi tiết (SDD) đã trình bày đầy đủ kiến trúc tổng thể, cơ chế xác thực – phân quyền, thiết kế lớp cho 10 module nghiệp vụ, thiết kế cơ sở dữ liệu gồm 44 bảng và thiết kế giao diện người dùng của hệ thống TechStore, bám sát mã nguồn thực tế và yêu cầu trong tài liệu SRS.
Thiết kế đã đáp ứng các mục tiêu trọng tâm: quản lý sản phẩm theo thông số kỹ thuật động, quản lý tồn kho ở mức từng đơn vị theo Serial/IMEI, quy trình đặt hàng – thanh toán, và các nghiệp vụ hậu mãi (bảo hành, sửa chữa, hỗ trợ). Kiến trúc microservice kết hợp API Gateway giúp tách bạch trách nhiệm và thuận tiện mở rộng.
Một số hạng mục được ghi nhận để hoàn thiện trong tương lai: hiện thực hóa chức năng trả góp (UC-C08) và quản lý đối tác vận chuyển (UC-A05); xây dựng dịch vụ báo cáo riêng cho UC-A08; bổ sung module Đánh giá sản phẩm (Review); loại bỏ nhánh xác thực mật khẩu plain-text và chuyển sang cơ sở dữ liệu riêng cho từng dịch vụ khi mở rộng quy mô. Tài liệu này là cơ sở để đội phát triển hiện thực, đội kiểm thử lập kịch bản và các bên liên quan rà soát, phê duyệt.
